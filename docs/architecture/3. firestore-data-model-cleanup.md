# Firestore data model cleanup — Phase 0 + Phase 1

## Context

You asked for a review of the Firestore data model because sync between
collections "feels poorly done." A full audit (11 collections, every
cross-collection sync point traced) confirmed this isn't just a feeling —
one of the duplications **already caused a real production incident**: a
missing diff-guard let an unrelated field change re-trigger the
agenda→check-in push, which re-fired check-in's own listener, which
re-ran the check-in→agenda sync, sustaining a self-perpetuating loop
(~100 redundant `agenda.publish` writes/hour on one meeting — caught via
the audit log's collapsed-row UI, not because anyone noticed directly).
The existing fix (a guard that skips a no-op write) patches the symptom;
the two-copies-of-meeting-metadata design underneath it is still there
and can produce a similar bug again for a different field in the future.

This plan fixes that root cause, plus two other genuinely pointless
duplications, **without touching any document ID** — meeting numbers stay
exactly as they are. A separate, larger problem (meeting number — a
mutable, admin-typed field — used as the document ID across 4 collections
with no rename path) is real but has never actually caused a problem, and
fixing it is the highest-blast-radius change of everything found (it'd
touch document identity across every collection at once, including the
publicly-writable `checkins` collection used live during meetings). It's
**deliberately out of scope here** — documented at the bottom for later,
not planned in implementation detail.

## Phase 0 — Independent, low-risk cleanup (do first, any order)

### 0a. Merge `roleDefinitions` + `committeeRoleDefinitions`

Two fully separate collections/services/admin pages doing identical CRUD
on the identical `RoleDefinition` shape, with identical `firestore.rules`
(public read / `isAppAdmin()` write) — copy-pasted implementation, not a
real distinction. Merge into one collection with a `kind: 'meeting' |
'committee'` discriminator.

- `src/app/core/models/role-definition.models.ts` — add `kind` field.
- `src/app/core/services/role-definition.service.ts` — filter
  `activeRoles()`/`all()` by `kind`; treat a missing `kind` on old docs as
  `'meeting'` (avoids needing a migration script for existing
  `roleDefinitions` docs — just a fallback in the read path).
- `src/app/features/agenda-editor/services/committee-role-definition.service.ts`
  — removed; callers switch to `RoleDefinitionService` filtered by
  `kind: 'committee'`.
- `src/app/features/admin-roles/pages/admin-roles.component.ts` and
  `src/app/features/admin-committee-roles/pages/admin-committee-roles.component.ts`
  — both now point at the one service, each filtered/scoped to its kind.
- `firestore.rules` — drop the `committeeRoleDefinitions` block, keep one
  merged rule for `roleDefinitions`.
- **Migration**: one-time copy of every `committeeRoleDefinitions` doc
  into `roleDefinitions` with `kind: 'committee'` added. Old collection
  left in place (unused) until confirmed cut over — delete later, not in
  this pass.

### 0b. Stop writing the dead `cmt` snapshot into saved/published agendas

`AgendaSnapshot.cmt` is a full frozen copy of the committee roster, baked
in on every save/publish. Confirmed dead: `AgendaImportExportService`
explicitly discards the stored value on load, and `DocxService`'s only
caller always uses the live `AgendaStateService.cmt` computed — nothing
in the app ever reads a stored `cmt` back, in DOCX generation or
anywhere else.

- `src/app/features/agenda-editor/services/agenda-import-export.service.ts`
  — stop including `cmt` in `getSnapshot()`'s output.
- `src/app/features/agenda-editor/models/agenda.models.ts` — drop `cmt`
  from `AgendaSnapshot` (or make it optional if removing outright risks
  breaking `loadSnapshot()`'s typing — check when implementing).
- **No migration needed** — old stored values are inert, safe to leave
  forever (cosmetic-only cleanup, not required).

## Phase 1 — Eliminate the checkin/agenda meeting-metadata duplication (the incident fix)

**Root cause**: `checkins/{meetingId}.meeting` is a second, persisted copy
of 7 fields (`date/theme/word/start/club/sub/addr`) that also live in the
agenda's own `MeetingData`. A one-way push effect in
`agenda-editor.component.ts` kept them in sync on every edit — that's the
mechanism that fed back on itself. Fix: give these fields **one live
source of truth** that both sides read from, so there's nothing left to
push and no feedback path left to sustain a loop.

### New collection: `meetings/{meetingNo}`

Same doc-id scheme as today (the meeting number string, unchanged — no ID
migration). Fields: `no, date, theme, word, start, club, sub, addr,
updatedAt, updatedBy`. Rules: public read (check-in/preview need it
unauthenticated), admin-only write.

**`savedAgendas`/`publishedAgendas` keep their own copies of these fields**
inside their stored `MeetingData` — deliberately, unchanged. A saved or
published agenda is a point-in-time snapshot; it should render its own
metadata as it was when saved, not silently reflow if someone edits a
since-superseded meeting doc later. Only the **live editing session** and
**check-in** read `meetings/{meetingNo}` live — don't touch the snapshot
collections' own copies.

### No new debounced push effect — fold the write into the existing explicit Save/Publish

Confirmed: `SavedAgendaService.save()` and `PublishedAgendaService.publish()`
already write via `writeBatch()` (the agenda doc + an audit entry,
atomically). Add a `meetings/{no}` upsert into that **same batch** in
both places — no new timer/effect machinery needed at all, and it can
never drift out of sync with what was actually saved, since it updates
exactly when the source data changes. This is a deliberate simplification
over the old "push on every keystroke, debounced" design, and matches
this app's recent move away from auto-save toward an explicit Save
button (see `agenda-editor.component.ts`'s `isDirty`/Save button, already
in place) — meeting-metadata edits should commit on the same explicit
Save click as the rest of the agenda, not on a separate always-live path.

### `checkins/{meetingNo}` — drop the `meeting` sub-object, keep `maxSpeakers`

`maxSpeakers` is genuinely check-in-only — confirmed zero references in
`agenda-editor.component.ts`; the agenda never sets or reads it. It needs
to survive as its own top-level field, not disappear along with the rest
of the removed `meeting` object.

New shape: `{ maxSpeakers: number, attendees: Attendee[], roles: {...},
speakers: [...], lockedRoles: [...], apologies: [...] }`.

### Code changes

- **New `MeetingsService`** (e.g.
  `src/app/features/agenda-editor/services/meetings.service.ts`) — small,
  live `onSnapshot` per meeting number, same idempotent `loadMeeting(no)`
  shape already used by `CheckinStateService`/`PublishedAgendaService`.
- **`src/app/features/checkin/services/checkin-state.service.ts`** —
  `meeting` computed repointed to read from `MeetingsService` instead of
  `snapshot().meeting`; `updateMeeting()` deleted entirely (check for any
  remaining call site setting `maxSpeakers` through it specifically — if
  none exists beyond `resetAll()`'s own default, no replacement method is
  needed at all).
- **`src/app/features/agenda-editor/pages/agenda-editor.component.ts`** —
  delete the debounced agenda→checkin reverse-sync effect entirely
  (`lastPushedMeetingJsonByNo` and everything around it).
- **`src/app/features/agenda-editor/services/checkin-agenda-sync.service.ts`**
  — the check-in→agenda direction (roles/speakers/apologies) is
  **unchanged**; Phase 1 only removes the reverse direction and the
  duplicate storage. While this file is open anyway, also add a
  persisted `syncedRolePersons?: Record<roleId, name>` field (mirroring
  the existing `apologySyncUids` pattern) so the role-release guard
  survives a reload the same way the apologies guard already does —
  bundled in for consistency, not because it's independently urgent (its
  current in-memory-only failure mode is mild: a released role's name
  lingers until someone else claims it or an admin notices before
  publish — nothing like the apologies feedback-loop class of bug).
- **`firestore.rules`** — add a `meetings/{meetingId}` block (public
  read / `isAppAdmin()` write); `checkins` rule is unchanged (still
  public read/write, now just covering a smaller document).
- **One-time backfill script** — for every existing meeting number found
  across `checkins`/`savedAgendas`/`publishedAgendas`, upsert
  `meetings/{no}` from the best-available source (prefer the
  most-recently-updated saved/published `MeetingData`; fall back to the
  existing `checkins/{no}.meeting` copy only if no agenda doc exists for
  that number). Idempotent — safe to re-run.

### Deploy ordering (live production app — real users, real meetings)

1. Deploy `meetings` collection rules + `MeetingsService` + the backfill
   script run — purely additive, nothing reads from it yet.
2. Repoint `CheckinStateService.meeting` to read the new service live —
   confirm check-in pages render correctly before proceeding.
3. Fold the `meetings/{no}` upsert into `SavedAgendaService.save()` /
   `PublishedAgendaService.publish()`'s existing batches.
4. Delete the reverse-sync effect and `updateMeeting()` — do this step
   last, once 1-3 are confirmed working, so there's a rollback window
   where the old push mechanism could still technically run if something
   looks wrong.
5. Leave `checkins.meeting`'s old field in place, unused, for a few days
   before a follow-up cleanup deploy removes it outright — cheap rollback
   safety net for a change touching the live check-in board.

## Explicitly out of scope for this pass

- **Stable `meetingId` replacing the mutable meeting-number-as-document-ID**
  across `checkins`/`savedAgendas`/`publishedAgendas`/`memberHistory`.
  Real issue (no coordinated rename path exists today), but no confirmed
  real-world need for renaming a meeting has ever come up, and it's a
  full document-identity migration across every collection at once —
  needs its own maintenance window, dual-read fallback, and tested
  rollback, done separately later if it ever becomes an actual need.
- **`checkins` vs `memberHistory` reconciliation** — these are two
  intentionally different records (public self-report vs admin-confirmed
  official record), not accidental duplication. Not merging or
  auto-syncing them; a real fix would need backend infrastructure
  (a Cloud Function trigger) this client-only app doesn't have, for a
  low-stakes divergence risk.
- **`members/{uid}` vs Firebase Auth `displayName` two-phase commit** —
  a real platform constraint (an Auth SDK write can't join a Firestore
  batch), not a schema issue. Firestore stays the actual source of truth
  (it's what the app reads everywhere); Auth's copy is accepted as
  best-effort/cosmetic.

1. `npm run build` — catches type errors from the model/service changes.
2. `npm run test:emulator` (with the emulator running) — the
   `role-definition`/`committee-role-definition`/`saved-agenda`/

   an existing number, edit the theme/date, click Save — confirm
   `meetings/{no}` updates in the Firestore emulator UI in the same

   tab/device and confirm it shows the updated theme/date without the
   old push mechanism.

   trigger an apologies sync (mark someone "Not Attending" on check-in)
   and confirm the audit log shows exactly one `agenda.publish`/save
   entry, not a burst of duplicates.
5. Confirm `/admin/roles` and `/admin/committee-roles` still list the
   correct roles after the Phase 0a merge, and that creating a new role
   on each page tags it with the right `kind`.
