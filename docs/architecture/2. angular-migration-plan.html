04 · Phase 4's open question: check-in state is per-browser

The check-in page's entire purpose is being a shared sheet — several members checking it at once before a meeting. Right now, "shared" isn't real: CheckinStateService persists to localStorage, so two people on two devices each see their own independent copy. This was a deliberate choice to unblock building and testing the role-locking logic (claim/release, first-come-wins, self-evaluation blocking) without standing up a Firebase project first — not step one of a Firebase rollout that got left half-finished.

The swap-in path is already scoped: CheckinStateService's public methods stay the same; only their internals move from localStorage reads/writes to Firestore's docData() / updateDoc() / runTransaction(). No component changes. Firestore was chosen over a custom MongoDB + Spring Boot + Render + Auth0 stack specifically because its transactions give atomic role-locking for free and its listeners give live cross-device sync for free — see the separate backend comparison doc for the full reasoning.
