Meeting Signup Page

A shared, real-time sheet where members claim roles, register as speakers, and confirm attendance — before walking in the door.

01 · Purpose

The agenda generator produces the plan. This page is the live layer on top of it — a digital sign-in sheet that feeds confirmed data back into the meeting. Members open a link, enter their name, and claim what they're doing that evening. The VPE sees, in real time, who is coming and what still needs filling.

02 · User flow
1
Open the link VPE shares a meeting-specific URL (e.g. /signup?meeting=163). The meeting header — date, theme, word of the day — is shown read-only at the top.
2
Enter your name A single text field. Once confirmed, the name is stored in the browser (localStorage) so it persists on revisit. This registers attendance.
3
Claim a role (optional) A list of all agenda roles. Available roles show a Claim button. Taken roles show the name of the person who claimed them — the button is gone.
4
Sign up to speak (optional) Members fill in: speech title, Pathways project / level, preferred time slot (5–7 or 7–10 min). A slot cap (set by VPE) prevents overbooking.
5
Volunteer to evaluate (optional) Each confirmed speaker slot shows an "Evaluate this speech" button. A member can claim one evaluation. Once claimed, it locks and shows the evaluator's name.
6
VPE exports to agenda An admin view (password-protected or separate URL) shows the full confirmed state and offers a one-click "Push to agenda" that pre-fills the generator's form fields.
03 · Page sections

Meeting header

Read-only. Club name, date, theme, word of the day, start time. Pulled from the meeting record.

Attendance

Name entry + submit. Shows a live count and a list of who's coming, sorted by signup time.

Role board

All roles from the agenda template. Claim / release. Taken roles are locked with the claimer's name visible.

Speakers

Add a speech slot. Fields: title, project, time preference. Shows who's registered with their evaluator if assigned.

Evaluations

Each speaker row has an open evaluator slot. Members claim it. One evaluation per member maximum.

Admin panel

Reset a role, cap speaker slots, push confirmed data to the agenda generator. Accessible via passphrase.

04 · Role locking — how it works

The first-come rule is enforced server-side, not client-side. The client sends a claim request; the server checks atomically whether the slot is free and either grants it or rejects it. The UI never assumes success until the server confirms.

Release: A member can release their own role at any time. They cannot release someone else's. The VPE admin panel can override any slot.

Concurrency: If two people click "Claim" simultaneously, only one wins. The other sees "Just taken by [Name]" and the slot updates live without a page refresh.

06 · Real-time sync — options
OptionHow it worksSetup effortCost
Firebase Realtime DB Recommended Google's hosted WebSocket DB. Add the SDK to the page, write rules. No server code. Updates propagate in ~100 ms. Low — create a project, paste config keys Free tier: 1 GB storage, 10 GB/month transfer
Supabase PostgreSQL + real-time subscriptions. More structured, easier to query, slightly more setup. Low–Medium Free tier: 500 MB DB, 2 GB bandwidth
Python + polling Extend the existing HTTP server to serve/save a JSON file. Page polls every 5 s. Simple but not instant. Low — ~50 lines of Python Free (runs locally)
Python + WebSockets Add a WebSocket endpoint alongside the HTTP server (e.g. with websockets or FastAPI). True real-time, self-hosted. Medium Free (runs locally or on a small VPS)

Recommendation: Firebase Realtime Database. No backend to maintain, atomic writes prevent race conditions on role claims, free tier comfortably covers a club of this size, and the SDK is a single script tag. The locking rule is two lines of Firebase security rules.

07 · Integration with the agenda generator
Agenda Generator Publishes the meeting record (date, theme, roles list, speaker slots) to Firebase when the VPE clicks "Share signup link."
⟷
Signup Page Reads the same record. Members fill roles and speakers. Confirmed state lives in Firebase.

When the VPE is ready to generate the final agenda, one click in the generator reads the confirmed signup data from Firebase and pre-fills all form fields — roles, speakers, evaluators — automatically.

08 · Build phases
Phase 1

Foundation

Static signup page — no real-time

  • HTML page with name entry, role list, speaker form
  • State stored in localStorage (single-device only — proof of concept)
  • Visual design and mobile layout finalized
  • Role locking logic written and tested (will plug into real backend in Phase 2)
Phase 2

Live sync

Firebase integration — real-time, multi-user

  • Firebase project created, security rules written
  • Real-time listeners replace localStorage reads
  • Atomic claim/release writes with server-side validation
  • Agenda generator gains "Share signup link" and "Import confirmed" buttons
Phase 3

Polish

Admin tools + edge cases

  • VPE admin panel: reset roles, set speaker cap, export
  • Duplicate name detection (warn, not block)
  • Meeting closure: VPE locks the signup sheet at start time
  • Push notification or email summary to VPE when key roles fill
09 · Open questions

A few decisions to make before building:

  • Roles list — should it be fixed (the standard Agora roles), or pulled dynamically from the agenda template so the VPE can add/remove roles per meeting?
  • Name verification — names are free text; no login. Is a simple "confirm your name" pattern enough, or should the system cross-reference a member list?
  • One role per person — can a member claim more than one role (e.g. Grammarian + speaker), or should the system enforce one claim per person?
  • Hosting — the current Python server runs locally. For members to access the signup page remotely (before the meeting), the server or the Firebase-backed page needs to be publicly reachable. Is that in scope?
